LAYER ONE · THE ONLY CONCEPT

Widget —— Flutter 的唯一概念

一句话：Flutter 里所有东西都是 Widget。 按钮是 widget，一段间距是 widget（SizedBox），甚至"内边距"也是 widget（Padding）。

核心心智模型

Widget 不是屏幕上的像素，它是一份配置说明书（immutable 描述）。 Flutter 拿这份说明书去构建真正的渲染树。所以 widget 全用 const 构造——它们只是数据。

StatelessWidget：没有内部状态

screens/projects/discovery_screen.dart:17
class DiscoveryScreen extends StatelessWidget {
  const DiscoveryScreen({super.key});      // super.key 把 key 转发给父类

  @override
  Widget build(BuildContext context) {     // 唯一必须实现的方法
    return const BrutalScaffold(
      title: 'The Plaza',
      titleBarColor: Palette.lime,
      body: PlazaBody(),
    );
  }
}
  • super.key —— key 是 Flutter 用来在重建时识别"这还是同一个 widget 吗"的身份标记
  • BuildContext context —— 你在 widget 树里的位置句柄。 用它可以向上查找祖先（Theme.of(context)、context.read<Provider>()）

为什么它是 Stateless？ 因为它的样子完全由传进来的参数决定，自己不记任何东西。 给同样的输入永远画出同样的东西。

为什么 StatefulWidget 要拆成两个类？

因为 Widget 本身是 immutable、会被频繁丢弃重建的；而状态必须活得比 widget 久。 所以 Flutter 把状态放进独立的 State 对象——父组件重建时， widget 实例被换掉了，但 Flutter 会复用同一个 State 对象， _stageFilter 的值就保住了。

在 State 里访问 widget 的参数用 widget.xxx， 例如 home_shell.dart:71 的 _index = widget.initialIndex;

生命周期：initState / dispose

必考

为什么要 _searchController.dispose()？

TextEditingController 内部持有监听器，不释放会内存泄漏。 规则：凡是你 new 出来的 Controller / AnimationController / StreamSubscription，都要在 dispose 里释放。

高频追问

addPostFrameCallback 是干嘛的？

在 initState 里不能直接调用会触发 notifyListeners() 的方法。 因为那一刻 widget 树正在构建中，Provider 通知监听者重建会抛 setState() or markNeedsBuild() called during build。

addPostFrameCallback 把 _refresh() 推迟到当前这一帧画完之后再执行，就安全了。 这个点你如果能主动说出来，会显得非常懂。

IndexedStack 为什么不用 if/else 或者直接 children[index]？

这是个真实的 trade-off，能说清楚就是满分回答。

context.push 和 context.go 的区别？

  • push —— 压栈，可以按返回键回来
  • go —— 替换整个栈，回不去了

redirect —— 你的路由守卫（最容易被深挖）

router.dart:53-108 实现了三步 onboarding 强制流程：

router.dart · Trust Gateway 守卫
redirect: (context, state) {
  if (!auth.bootstrapped) return null;   // 还没恢复会话，先不拦

  // 完全 onboarding 完成 → 放行，只把 / 和 /onboarding/* 送去 /home
  if (onboardingComplete) {
    if (loc == '/' || loc.startsWith('/onboarding')) return '/home';
    return null;
  }
  // STEP 1 —— 还没有 user：必须先连 GitHub
  if (user == null) {
    return loc == '/onboarding/github' ? null : '/onboarding/github';
  }
  // STEP 2 —— GitHub 连了，LinkedIn 没绑
  if (!linkedinConnected) { ... return '/onboarding/linkedin'; }

  // STEP 3 —— LinkedIn 绑了，角色没选
  return loc == '/onboarding/role' ? null : '/onboarding/role';
}

关键规则：return null 表示"放行，不重定向"； 返回一个路径字符串表示"跳到那里去"。

必考

refreshListenable: auth 是什么？

AuthProvider 是个 ChangeNotifier。 每次它调 notifyListeners()（比如 loadMe() 拿到用户、 confirmRole() 改完角色），go_router 就会重新跑一遍 redirect。

所以状态一变，路由守卫自动重新判定。这就是"声明式路由"的含义—— 你不手动 push，你只描述"什么状态该在什么页面"。

陷阱题

为什么每个分支都要写 loc == 'xxx' ? null : 'xxx'？

防止无限重定向循环。如果已经在 /onboarding/github 了 还返回 '/onboarding/github'，redirect 会被反复触发， go_router 会抛 redirect loop 异常。所以"目标就是当前位置"时必须返回 null。

进阶 · 你代码最聪明的一段

router.dart:48 那个 linkedinResync 布尔量为什么存在？

LinkedIn 真实 OIDC 登录是整页重定向回来，回来时 URL 带 ?linkedin=ok，但本地的 currentUser 还是旧的（LinkedIn 未绑定）。所以要重新 loadMe() 一次。

但 loadMe() 会 notifyListeners() → 触发 redirect 重跑 → 又会 loadMe() → 死循环。 这个一次性标志位打破了循环。因为整页重定向本身就是一次完整重载，这个变量自然会重置。

这是讲师最可能挑出来问的一段。务必背熟。

.value 和 create: 有什么区别？为什么 auth 用 .value？

  • create: —— Provider 负责创建，并且负责 dispose
  • .value —— Provider 只是引用一个已存在的对象，不负责它的生命周期

③ 消费：watch vs read（最高频考点）

行为用在哪
context.watch<T>() 订阅 —— T 调 notifyListeners 时，本 widget 重建 build() 方法里
context.read<T>() 只取一次，不订阅 事件回调 / initState 里
discovery_screen.dart:64-83

  final provider = context.watch<ProjectsProvider>();   // 要显示列表 → 订阅
  final growth   = context.watch<GrowthProvider>();
  ...
}

Future<void> _refresh() {
  return context.read<ProjectsProvider>().fetchDiscovery(...); // 只发起动作 → read

双向陷阱

在 onPressed 里用 watch 会怎样？ 会抛异常或造成不必要的重建。watch 必须在 build 期间调用才能建立订阅关系； 而且回调只是要"触发一个动作"，根本不需要订阅。

反过来，在 build 里用 read 会怎样？ 界面不更新——数据变了但没人通知这个 widget 重建。

你的 discovery_screen 两边都用对了，可以直接指着讲。

一次完整的状态流转（务必能完整复述）

以"用户在 Plaza 选了 stage 筛选"为例：

1
用户点 BrutalDropdownUI EVENT
2
onChanged → setState(() => _stageFilter = stage)本地 UI 状态
3
_refresh() → context.read<ProjectsProvider>().fetchDiscovery(stage: ...)触发动作，不订阅
4
Provider：_loadingDiscovery = true; notifyListeners();→ watch 它的 PlazaBody 重建 → 显示 CircularProgressIndicator
5
await _api.dio.get('/projects', queryParameters: {...})网络请求，不阻塞 UI
6
_discovery = _parseList(res.data)JSON → List<ProjectCard>
7
finally { _loadingDiscovery = false; notifyListeners(); }→ 再次重建 → 渲染卡片列表
值得主动说

notifyListeners() 被调了两次——一次进入 loading 态，一次数据到位。 而且第二次放在 finally 里，保证即使抛异常也一定会关掉 loading。

LAYER FIVE · ASYNC

异步 —— Future / async / await

state/projects_provider.dart:75
Future<void> fetchDiscovery({String? stage, String? q}) async {
  _loadingDiscovery = true;
  notifyListeners();
  try {
    final res = await _api.dio.get<List<dynamic>>('/projects', ...);
    _discovery = _parseList(res.data);
  } catch (e) {
    _error = ApiClient.describeError(e);
    // NFR 离线降级：读 SharedPreferences 缓存
  } finally {
    _loadingDiscovery = false;   // 无论成功失败都执行
    notifyListeners();
  }
}
  • Future<T> = "以后会给你一个 T"，等价于 JS 的 Promise
  • async 标记这个函数是异步的，它会立刻返回一个 Future，不阻塞 UI
  • await = 暂停这个函数，等 Future 完成，拿到结果继续。不阻塞主线程，UI 依然流畅
  • Future<void> = 会完成，但没有返回值（只关心"做完了没"）
最经典的 async 陷阱

home_shell.dart:364-368：

Future<void> _logout(BuildContext context) async {
  await context.read<AuthProvider>().logout();
  if (!context.mounted) return;              // ← 这一行
  context.go('/onboarding/github');
}

if (!context.mounted) return; 是干什么的？

await 期间用户可能已经离开了这个页面，widget 被销毁了。 这时候再用 context 去导航或 showSnackBar，会崩溃 （Looking up a deactivated widget's ancestor）。 context.mounted 检查这个 widget 是否还在树上。

这是 Flutter 官方 lint 规则 use_build_context_synchronously 强制要求的。 你在 home_shell.dart:379 和 :382 也做了。 能说出这个，会显示你不是复制粘贴来的。

  late final Dio _dio;
  Dio get dio => _dio;
}
  • ApiClient._internal() 是命名构造函数 + 私有（下划线）→ 外部无法 new ApiClient()
  • static final instance → 全局唯一实例，第一次访问时创建（Dart 的 static final 是 lazy 的）

为什么要单例？ Dio 内部维护连接池和拦截器，每个请求都新建一个 Dio 会浪费资源，而且拦截器要重复注册。

}

RAPID FIRE · 20 QUESTIONS

20 题快问快答

先自己在心里答一遍，再点开对答案。目标是每题 15 秒内说清楚。

StatelessWidget 和 StatefulWidget 什么时候用哪个？

看它有没有需要跨重建保留的内部状态。 样子完全由参数决定 → Stateless。有 controller、有开关、有本地筛选值 → Stateful。 默认选 Stateless，需要了再升级。

为什么 Widget 是 immutable 的？

因为 widget 只是配置说明书，Flutter 每帧都可能重建它们。 immutable 让重建变得极廉价（只是创建描述对象），真正昂贵的渲染对象（RenderObject）被复用。 状态则放在独立的 State 里，活得比 widget 久。

BuildContext 到底是什么？

它是你这个 widget 在树里位置的句柄。 通过它可以向上查找祖先——Theme.of(context)、MediaQuery.of(context)、 context.read<Provider>() 全都是"从我这个位置往上找"。

setState 做了什么？不调用会怎样？

两件事：执行回调改状态；把这个 Element 标记为 dirty， Flutter 下一帧会重新调用它的 build()。不调用 setState， 字段虽然改了但界面不会刷新。

为什么在 initState 里要用 addPostFrameCallback？

因为 initState 执行时 widget 树正在构建中， 直接调会 notifyListeners() 的方法会抛 setState() called during build。 addPostFrameCallback 把它推迟到这一帧画完之后。

context.watch 和 context.read 的区别？

watch 建立订阅——被监听的 ChangeNotifier 一 notify，本 widget 就重建， 只能在 build 里用。read 只取一次不订阅， 用在事件回调和 initState 里。用反了：build 里 read → 界面不更新； 回调里 watch → 报错。

ChangeNotifierProvider 的 .value 和 create: 差在哪？

create: Provider 负责创建并 dispose； .value 只是引用现成对象，不管生命周期。 我们的 _auth 在 main 的 initState 里手动创建（因为路由要它）， 手动 dispose，所以必须用 .value，否则会被 dispose 两次。

为什么用 6 个 Provider 而不是 1 个大的？

重建粒度。只 watch ProjectsProvider 的 widget 不会因为 MarketProvider 变化而重建。 按 feature 切分（auth / projects / growth / matches / collab / market） 也让每个类的职责清晰、可以单独测试。

notifyListeners 为什么放在 finally 里？

保证无论请求成功还是抛异常，loading 状态一定会被关掉， UI 不会永远卡在转圈。同一个方法里 notify 两次：一次进 loading，一次出结果。

context.push 和 context.go 什么时候用哪个？

push 压栈、可返回——进详情页、进表单用它。 go 替换整个栈、回不去——登出、 onboarding 完成进主页用它。登出必须用 go， 否则按返回键能回到已登录页面。

go_router 的 redirect 返回 null 是什么意思？

放行，不重定向。返回字符串才是"跳到那里去"。 所以每个分支都要写 loc == 'xxx' ? null : 'xxx'—— 已经在目标位置时必须返回 null，否则无限重定向循环。

refreshListenable 起什么作用？

把 AuthProvider 交给 go_router 监听。 它每次 notifyListeners()，redirect 就重跑一遍。 所以登录、绑定 LinkedIn、选角色之后，路由守卫自动重新判定该停在哪一步—— 这就是声明式路由：我不手动 push，我只声明"什么状态该在什么页面"。

路由里那个 linkedinResync 布尔量为什么存在？

LinkedIn 真实 OIDC 是整页重定向回来，回来时本地 user 还是旧的， 必须重新 loadMe()。但 loadMe 会 notify → redirect 重跑 → 又 loadMe → 死循环。这个一次性标志位打破循环； 因为整页重定向本身就是完整重载，变量自然重置。

Future 和 async/await 的关系？

Future<T> 是"以后会给你一个 T"的凭证。 async 让函数立刻返回一个 Future 而不阻塞； await 暂停这个函数直到 Future 完成， 但不阻塞主线程，UI 照常渲染。

await 之后为什么要检查 context.mounted？

await 期间用户可能已经离开页面，widget 被销毁。 这时再用 context 导航或弹 SnackBar 会抛 Looking up a deactivated widget's ancestor。 这是官方 lint use_build_context_synchronously 强制的。

ApiClient 为什么做成单例？

Dio 内部维护连接池和拦截器链。每次请求 new 一个既浪费资源， 又要重复注册拦截器。私有构造 ApiClient._internal() + static final instance 保证全局唯一，且 Dart 的 static final 是惰性初始化的。

拦截器解决了什么问题？

把 Authorization: Bearer <token> 的注入 集中到一处，而不是在 58 个文件的每次调用里手写 header。 DRY。而且 token 从 SharedPreferences 读、内存缓存，也统一在这里。

上传截图为什么要用另一个"裸" Dio？

两个理由：① 安全——不能把我们的 Bearer token 发给第三方对象存储； ② 技术——预签名 URL 本身就是凭证，多余的 Authorization header 会破坏 S3 签名校验导致失败。Content-Type 也必须跟签名时完全一致，否则 403。

fromJson 里为什么全是 as String? ?? 默认值？

防御式解析。后端是并行开发的，少一个字段或类型不对， 如果直接 as String 就抛异常、整个列表页白屏。 降级成合理默认值，用户至少能看到其他内容。同理 whereType<Map<String, dynamic>>() 会跳过数组里的脏数据。

IndexedStack 和条件渲染的取舍？

IndexedStack 把 4 个 tab 全建好留在树里，只显示一个—— 切 tab 不丢状态（滚动位置、搜索框、已加载数据都在）， 代价是内存占用高。条件渲染省内存但每次切换都销毁重建、要重新请求网络。 底部导航这种高频切换的场景，IndexedStack 是对的选择。
