为什么我没用课上教的那个写法

这一节是整份手册最重要的部分。 交叉课件 + Lab 参考代码后的结论：你的技术栈和课上实际教的有相当大的偏离。而讲师明说 "When I will look into your code, I will know immediately this is not your code"，并且会在 viva 现场判断 AI 使用程度。

高危 ① 为什么用 go_router，不用 Navigator.push / 命名路由？

课上教的： Lab 6 深教 Navigator.of(context).push<GroceryItem>(MaterialPageRoute(...))；Lab 8/9/11 用 routes:{} + pushNamed。go_router 零覆盖。

因为我需要集中式的登录门禁。我们的 Trust Gateway 要求 GitHub → LinkedIn → 选角色三步走完才能进主页。如果用 Navigator，我得在每一个屏幕的 initState 里各写一遍"没登录就踢回去"，19 个路由就是 19 份重复逻辑，而且漏一个就是个洞。

go_router 给我一个顶层 redirect 回调——所有导航都要先过它，守卫只写一份（router.dart:53-108）。配合 refreshListenable: auth，AuthProvider 一 notifyListeners() 守卫就自动重跑，登录状态变了页面自己会跳，不用我手动 push。

另外我们要跑 Web，go_router 原生支持 URL 深链和浏览器前进后退；Navigator 的栈式导航在 Web 上地址栏不会变。

追问"那 Navigator 你会用吗" → 会，router.dart:154-158 的 /projects/:id 就是路径参数，等价于 MaterialPageRoute 传构造参数；context.push 对应 Navigator.push（压栈、能返回），context.go 对应 pushReplacement（替换栈）。

高危 ② 为什么用 dio，不用课上教的 http 包？

课上教的： Lab 6 深教 http.get(Uri.https(...)) + json.decode 手写解析。

核心原因是拦截器。我们所有接口都要带 Authorization: Bearer。用 http 包的话，每一次调用都得手写 headers: {'Authorization': ...}——我有 30 多个接口调用，就是 30 处重复，而且新加一个接口忘了写就是 401。

dio 的 InterceptorsWrapper 让我只在一个地方挂 token（api_client.dart:31-41），provider 里写 _api.dio.get('/projects/mine') 就行，完全不用管鉴权。

另外 dio 直接给我 baseUrl、connectTimeout/receiveTimeout，还有类型化的 DioException——我靠 error.type 区分"连不上后端"和"后端太慢"，给用户两句不同的话（api_client.dart:99-108）。http 包只会抛一个笼统的 SocketException。

加分补一句： "而且我没有关掉 dio 的默认 validateStatus——4xx 照样抛异常，因为我的调用方全是 try/catch 加 describeError，靠抛异常来分流。api_client.dart:20-24 我特意留了注释说明不要加宽松的 validateStatus。"

高危 ③ import 'a.dart' if (dart.library.io) 'b.dart' 这是什么？

这叫条件导入（conditional import），是 Dart 的编译期平台分支——不是运行时 if。见 api_client.dart:5-6、auth_provider.dart:9-10、projects_provider.dart:9-10。

import 'connection_tuning_web.dart'
    if (dart.library.io) 'connection_tuning_io.dart';
编译到 Web 时 dart.library.io 不存在，走 _web.dart（空实现，浏览器自己管连接池）；编译到 Android/iOS 时走 _io.dart。两个文件必须导出同名函数 tuneConnectionReuse(Dio)，调用方只写一次。

为什么必须这么做：_io.dart 里 import 'dart:io'，而 dart:io 在 Web 上根本不存在，直接 import 会编译失败。运行时 if (kIsWeb) 救不了——那时代码已经编译进去了。

然后他一定会问"那你调了什么" → 见 §02 第 ④ 条，这是你最强的一张牌。

强项 ④ idleTimeout = 3s 是干嘛的？（把这个讲出来）

connection_tuning_io.dart 全文 23 行，但这是你整个代码库里最能证明"这是我写的"的一段——因为它记录的是一个只有亲自 debug 过才知道的事故。

void tuneConnectionReuse(Dio dio) {
  dio.httpClientAdapter = IOHttpClientAdapter(
    createHttpClient: () =>
        HttpClient()..idleTimeout = const Duration(seconds: 3),
  );
}
Dart 的 HttpClient 会把空闲的 keep-alive 连接在池子里留 15 秒。但我们后端跑的是 Uvicorn，它5 秒就把空闲连接关掉了。

中间这 10 秒是个死亡窗口：客户端以为连接还活着，把请求写进一个服务端已经关掉的 socket，然后永远等不到回复，最后报 receiveTimeout——而服务器日志里一行都没有，因为请求根本没到。

我是在截图上传时踩到的：相册选择器开了一分钟，回来第一次上传就静默卡 10 秒。把客户端的 idle timeout 压到 3 秒，压到服务端的 5 秒以下，这个窗口就不存在了。
战术建议：如果他问"你遇到过什么难的 bug"，讲这个，不要讲别的。它同时证明了：你懂 HTTP keep-alive、你真的调过、你知道为什么要条件导入。

中 ⑦ 为什么用 context.watch/read 而不是 Provider.of / Consumer？

课上教的： Provider.of<T>(context) / Provider.of<T>(context, listen: false) / Consumer<T>(builder:)。

它们是同一个东西——context.watch<T>() 就是 Provider.of<T>(context, listen: true) 的扩展方法语法糖，context.read<T>() 就是 listen: false。provider 6 之后官方推荐前者，因为名字直接说清了会不会订阅，不像 listen 那个布尔参数容易写错。

我的规矩是：build() 里用 watch，回调和 initState 里用 read。反过来会出两种事故——在 build 里 read，数据变了 UI 不刷新；在按钮回调里 watch，会在错误的生命周期建立订阅。

Consumer 我没用，因为它的价值是缩小重建范围——只重建 builder 里那一小块。我的屏幕本身就已经拆成很多小 widget 了（_IntentSection、_ProjectsSection、_ProjectRow），每个自己 watch，粒度已经够细，再包一层 Consumer 只是多一层嵌套。
中 ⑧ abstract final class Palette —— 这两个修饰符是什么？

Dart 3 的类修饰符。abstract = 不能被实例化（没有 Palette()），final = 不能被继承或实现。合起来表达"这是一个纯静态常量容器，不是一个类型"。

写成普通 class 的话，别人可以 Palette() 造一个毫无意义的实例，或者 extends Palette 搞出第二套颜色——那我"单一颜色来源"这个约定就破了。用类型系统把误用挡在编译期，比写注释靠谱。AppTheme、AppType、AppMotion 都是同样处理。

如果他说"没见过这个语法" → "是 Dart 3 引入的 class modifiers，之前只能靠私有构造函数 Palette._() 来模拟。"

中 ⑨ (Icons.home_filled, 'Home') 和 switch (role) { 'builder' => ... }？

两个 Dart 3 特性，都在 home_shell.dart：

  • Record（记录 / 元组） :36-41 — const _kNavItems = [(Icons.home_filled, 'Home'), ...]。取值用 .$1 / .$2。为什么：图标和文字必须成对，我不想为四个导航项专门定义一个 class；Record 是轻量的匿名值组合，还是 const 的。
  • switch expression :162-167 — String _roleTitle(String role) => switch (role) { 'builder' => 'Builder Home', ... _ => 'Home' };。和 switch 语句的区别：它是表达式，直接求值出一个 String，不需要 case ... return ... break；_ 是默认分支；编译器会检查穷尽性。
中 ⑩ 为什么 fromJson 全手写，不用 json_serializable / freezed？
因为我要防御式解析。后端是我们三个人并行开发的，字段随时可能缺、类型可能对不上。codegen 生成的 fromJson 遇到缺字段直接抛异常——一条脏数据就能让整个列表白屏。

我手写的每一个字段都有兜底（project_card.dart:157-176）：json['title'] as String? ?? ''，日期用 DateTime.tryParse（不会抛），嵌套对象用 is Map<String,dynamic> ? OwnerLite.fromJson(...) : 占位对象，列表用 .whereType<Map<String,dynamic>>() 静默过滤掉脏元素而不是整个炸掉。

第二个原因是 codegen 要引 build_runner，每改一次模型就得跑一次 flutter pub run build_runner build，在三人并行改接口的节奏下反而更慢。

追问"那 whereType 具体做什么" → 它是 Iterable<T> 的方法，把 List<dynamic> 里不是 Map<String,dynamic> 的元素直接丢掉，同时把静态类型收窄到 Iterable<Map<String,dynamic>>，所以后面能直接 .map(ProjectCard.fromJson) ——这里用的是构造函数撕裂（tear-off），等价于 .map((j) => ProjectCard.fromJson(j))。

安全 ⑪ 为什么用 Provider 而不是 Riverpod / BLoC？
这条你是对的，可以硬气回答。 课程讲义（Lecture 7）深教 Provider，Lab 8/11 参考代码里 Provider.of 用了 49 次；Riverpod 在 PPT 上只有一页 flutter pub add flutter_riverpod，没有任何代码或 Lab；BLoC 完全没提。
Provider 是这门课教的方案，也是官方推荐的入门方案。我们的状态很直白——六块领域数据，每块一个 ChangeNotifier，没有复杂的事件流，用不上 BLoC 那套 Event/State 建模。Riverpod 的优势是编译期安全和不依赖 BuildContext，但代价是一整套新概念，对三人两个月的项目不划算。

追问"ChangeNotifier 怎么工作" → 它维护一个监听者列表；notifyListeners() 逐个调用它们。ChangeNotifierProvider 在 widget 树上放一个 InheritedWidget，context.watch<T>() 向上找到它并注册当前 element 为监听者 → 通知时该 element 被标脏 → 下一帧重建。

中 ⑫ String.fromEnvironment？shared_preferences？? 这个符号？

a) config.dart 的编译期常量：

const String apiBaseUrl = String.fromEnvironment(
  'API_BASE_URL', defaultValue: 'http://builder-plaza-alb-...');
String.fromEnvironment 在编译时读取 --dart-define 传进来的值，所以它能是 const——跑起来之后改不了。本地开发用 flutter run --dart-define=API_BASE_URL=http://localhost:8000 就切到本机后端。默认值指向部署好的 ECS 后端，这样评分时 flutter run 零配置就能跑。

我知道这里有两个问题：生产地址写死在源码里，而且是明文 HTTP 不是 HTTPS。正式产品应该走 CI 注入 + TLS，这里是为了 demo 便利做的取舍。

b) shared_preferences： 课程大纲有 "Shared Preference" 词条但没有任何 Lab。你用它做两件事：存 JWT（api_client.dart:44,62-72）和离线缓存（见 §07）。一句话：它是键值对的本地持久化，底层在 Android 是 SharedPreferences、iOS 是 NSUserDefaults、Web 是 localStorage，只能存基本类型，所以我把对象 jsonEncode 成字符串再存。

c) 'context_ref': ?contextRef 里的 ?： 这叫 null-aware element（Dart 3.9+）——值为 null 时整个键值对不出现在 map 里。注意 这个语法在 Gao Xing 的 collab_provider.dart / market_provider.dart 里；你自己的 projects_provider.dart:151-154 用的是老写法 collection-if：if (needs != null && needs.isNotEmpty) 'needs': needs。如果他指着别人的文件问你，就照实说"那是 Gao Xing 写的，语义等价于我这边的 collection-if"。

1 · 为什么这个屏是 StatefulWidget，而项目列表却在 Provider 里？
我的分界线是"这个状态有没有第二个屏幕关心"。

表单里的输入内容、四个错误文案、_submitted、_saving——只有这一个屏幕关心，离开就该销毁。这种叫 ephemeral state，用 setState 就够了；放进 Provider 反而要手动清理，还会让全局状态越来越脏。

但"我的项目列表"首页要显示、详情页要更新、归档后 Plaza 要移除——三个屏幕共享，这就是 app state，必须放 Provider。

这正好是课程讲的 ephemeral state vs app state 那条线。
2 · TextEditingController 为什么必须 dispose？不 dispose 会怎样？

TextEditingController 本身是个 ChangeNotifier，TextField 会订阅它。屏幕销毁后如果不 dispose()，控制器和它的监听者列表不会被 GC 回收 → 内存泄漏；如果还有异步回调在往里写，还会触发"在已销毁的 widget 上 setState"。

@override

  _titleController.dispose();
  ... // 5 个全部释放
  super.dispose();   // ← 必须最后调
}

规则一句话：凡是在 initState / 字段初始化里创建的、带订阅的东西（Controller、Timer、StreamSubscription、AnimationController、FocusNode），都必须在 dispose 里释放，且 super.dispose() 放最后。

5 · _upsertMine —— 为什么造新 List 而不是原地改？ 
void _upsertMine(ProjectCard card) {
  final idx = _mine.indexWhere((p) => p.id == card.id);
  if (idx == -1) {
    _mine = [card, ..._mine];        // 新建 → 插到最前，用展开运算符造新表
  } else {
    final next = [..._mine];         // 更新 → 先复制
    next[idx] = card;
    _mine = next;
  }
}
两个原因。

一是不可变性更安全：_mine 的 getter 是直接暴露出去的，如果 UI 拿到的是同一个 List 实例，任何地方一个 .add() 就能绕过 provider 偷改状态，而且不会触发 notifyListeners()——变了但界面不刷新，非常难查。每次换一个新 List 实例，外面拿到的永远是快照。

二是"新建插到最前、更新留在原位"这个语义：用户改一个项目，它不该突然跳到列表顶部。

[card, ..._mine] 里的 ... 是展开运算符（spread），把旧列表的元素铺进新列表。

为什么要两个 Dio？（这是核心考点）

因为第二步是发给对象存储（S3），不是发给我们自己的后端。

预签名 URL 本身就是凭证——签名已经写在 query string 里了。如果我把我们的 Authorization: Bearer 也带过去，S3 会看到一个它不认识的认证头，和签名冲突，直接拒。

而我的 ApiClient 的拦截器是无差别给每个请求挂 token 的。所以我需要一个干净的、没有拦截器的 Dio 专门做这一步——就是 _storageDio（:32，注释在 :28-31）。

顺带一提，这也是为什么它是 final 字段而不是每次上传 Dio() 新建：复用连接池，而且构造时就调了 tuneConnectionReuse（:23）。

它是 StatefulWidget 只因为一个 bool _pressed——按下去的视觉反馈。

效果是这样做出来的：静止时按钮浮在一个 (4,4) 的硬阴影上；按下时同时把自己往右下平移 4px、并把阴影去掉——两件事一起发生，视觉上就是按扁贴到纸面上。用 AnimatedContainer 是因为它会自动在新旧属性之间补间，我不用写 AnimationController。

onTapCancel 必须处理：用户按下之后手指滑出按钮范围，onTapUp 不会触发，不补这个回调按钮就永远卡在按下状态。

widget.xxx 这个写法是因为在 State 类里访问配置要通过 widget 引用——Widget 是不可变的配置，State 是可变的状态，两者分开，这也是 StatefulWidget 为什么是两个类。

BrutalField —— 参数化复用的样板

一个 StatelessWidget，11 个可选参数，被项目表单用了 5 次、Intent 编辑器 1 次、职位表单若干次。讲它的重点是"错误态是怎么统一的"：errorText 非空时边框转 tomato 色、下面补一行红字（见文件末尾的 if (hasError) ...[...]）——所有屏幕的错误呈现自动一致，我不用在每个表单里重复写红边逻辑。

...[ ] 这个语法叫 collection-if + spread：if (cond) ...[a, b] 表示条件成立时把 a、b 两个元素铺进 children 列表。没有它就得写 cond ? Column(...) : SizedBox.shrink()，多一层无意义的嵌套。

主题层：为什么颜色只能从 Palette 取

theme/palette.dart 是全部颜色的单一来源，文件顶上就写着 "Never hard-code hex values in widgets"。

好处很实际：改一次主色，36 个 import 它的文件全部跟着变。如果散落在各处写 Color(0xFF1F7A6C)，改配色就是全局搜索替换，一定会漏。

另外颜色是有语义槽位的，不是随便取的：teal = 主操作，lime = 信任，mustard = 证据，tomato = 错误 / 模拟，copper = 意向。所以我选颜色是按"这块内容是什么意思"，不是按"哪个好看"。

AppType（theme/typography.dart）同理，三种字体各封装成静态方法：AppType.display() 标题、AppType.body() 正文、AppType.mono() 标签与数据。

这里有一个他可能挑的点：我这套排版绕过了 Theme.of(context).textTheme，每个 Text 直接调 AppType.body(size: 14)。
答法："因为我这套系统的尺寸是连续可调的，而 textTheme 是一组固定槽位（displayLarge / bodyMedium…），我需要的很多尺寸没有对应槽位。代价是没法通过切换 ThemeData 来整体换字体——如果要做深色模式或多主题，就必须改回 Theme.of(context)。AppTheme.build() 里我确实配了 ColorScheme.fromSeed 和 GoogleFonts.interTightTextTheme，那是给 Material 自带组件用的兜底。"

09 · 语法急救包

Fail 判据写着 "Poor syntax knowledge"

这是官方 rubric 里唯一把「Dart/Flutter 语法本身」写进 Fail 的地方。他不只问你的代码，会随口考基础。以下每条要能三句话之内答完。
Widget 基础
  • Stateless vs Stateful — 前者一旦构建其配置不变，只在父级重建或依赖变化时重建；后者有一个独立于 widget 生命周期的 State 对象，可以 setState 触发自己重建。判断标准：这个 widget 内部有没有会变的数据。
  • setState 做了什么 — 执行你的回调改字段，然后把该 element 标记为 dirty，Flutter 在下一帧重新调用它的 build。不是立刻重建。
  • 为什么必须在 setState 里改 — 直接改字段不会通知框架，界面不会刷新。
  • initState — State 创建后调一次，做订阅、初始化、发起首次加载。不能在里面用会依赖 InheritedWidget 的 context 操作。
  • dispose — State 永久移除时调一次，释放 controller / timer / 订阅。
  • BuildContext — 当前 widget 在树中位置的句柄，用来向上查找 InheritedWidget（Theme.of、context.read 都是它）。
  • const 构造函数 — 编译期创建、同参数复用同一个实例，Flutter 重建时能直接跳过它的子树 diff。
  • super.key — 把 key 传给父类。key 的作用是让 Flutter 在列表重排时认出"还是同一个 widget"，从而保留它的 State。
Dart 语言
  • final vs const — final 运行时赋值一次；const 编译期就确定。
  • late — 声明时不赋值但保证使用前会赋值；late final 用在必须延迟到 initState 才能构造的字段（main.dart 的 _auth / _router）。
  • ? / ! / ?? / ?. — 可空类型 / 断言非空（错了就崩）/ 为 null 时取右边 / 非 null 才调用。
  • 命名参数与 required — {required this.label, this.color = Palette.teal}：花括号内是命名参数，required 表示必传，= 给默认值。
  • _ 前缀 — Dart 没有 private 关键字，下划线开头 = 库级私有（同一个 .dart 文件内可见）。
  • factory 构造函数 — 不强制返回新实例，可以做解析、缓存、返回子类。所有 fromJson 都是 factory。
  • async / await / Future — Future<T> 是"以后会有一个 T"；async 标记函数返回 Future；await 挂起当前函数等它完成，不阻塞 UI 线程。
  • => — 单表达式函数体的简写。
  • ... — spread，把一个集合铺进另一个集合。
布局 · 列表 · 异步 UI
  • Column / Row — 主轴 mainAxisAlignment、交叉轴 crossAxisAlignment；Column 主轴是竖直。
  • Expanded — 在 Row/Column 里按 flex 瓜分剩余空间。_HomeTab 里两个 Expanded 就是让 Intent 和 Projects 各占一半。
  • SizedBox — 固定尺寸；只给一边就是间距。
  • Stack / Positioned — 层叠定位；_Thumb 用它把删除按钮压在缩略图右上角。
  • ListView vs ListView.builder — 前者一次构建全部 children；后者懒构建，只造可见项并回收滚出去的。数据量不确定就必须用 builder。
  • IndexedStack — 同时保留所有子节点的 State，只显示 index 那个。换 tab 不丢滚动位置和表单内容，代价是所有 tab 都被构建。对比：条件渲染 [a,b][i] 会销毁另一个的 State。
  • LayoutBuilder — 拿到父级给的 BoxConstraints，据此选布局。home_shell.dart:117 用 constraints.maxWidth >= 700 切 side rail / bottom nav。比 MediaQuery 好，因为它量的是"我被分到多大"，不是整块屏幕。
  • RefreshIndicator — 下拉刷新，onRefresh 返回一个 Future，转圈到它完成。_HomeTab:185-187。
  • context.mounted — await 之后 widget 可能已经被销毁了，此时再用 context 会崩。所有异步之后用 context 的地方都要先判。lint 规则名：use_build_context_synchronously。
概念题（MOCK 考过）

Ephemeral state vs App state — 前者只有一个 widget 关心、生命周期跟着它走（表单输入、当前 tab、按钮按下态），用 setState；后者跨屏共享、需要在屏幕间存活（登录用户、项目列表、离线缓存），用 Provider。
用你自己的代码举例： project_form_screen 的 _titleError 是 ephemeral，ProjectsProvider._mine 是 app state。

性能题 演练三 · 列表改成 ListView.builder

现状 home_shell.dart:319-322：

for (var i = 0; i < projects.mine.length; i++) ...[
  if (i > 0) const Divider(color: Palette.ink200, height: 18),
  _ProjectRow(project: projects.mine[i]),
]

改成（注意这一段外面已经被 SingleChildScrollView 包着，所以要给 shrinkWrap + 禁用内层滚动）：

ListView.builder(
  shrinkWrap: true,                              // 高度由内容决定，不抢无限高
  physics: const NeverScrollableScrollPhysics(), // 滚动交给外层，避免嵌套滚动打架
  itemCount: projects.mine.length,
  itemBuilder: (context, i) => Column(
    crossAxisAlignment: CrossAxisAlignment.start,
    children: [
      if (i > 0) const Divider(color: Palette.ink200, height: 18),
      _ProjectRow(project: projects.mine[i]),
    ],
  ),
)
ListView.builder 是懒构建：它只调用可见范围内那几项的 itemBuilder，滚出屏幕的会被回收。ListView(children:) 则是一次性把全部子 widget 都构建出来——数据量一大，首帧时间和内存都是线性增长。

这里有个坑要处理：这段外面已经有一个 SingleChildScrollView。ListView 默认想要无限高度，嵌在可滚动父级里会直接抛 unbounded height 错误。所以要加 shrinkWrap: true 让它按内容算高度，再加 NeverScrollableScrollPhysics 把滚动完全交给外层，否则两层滚动会互相抢手势。

不过说实话，shrinkWrap: true 会强制它一次性测量全部子项，懒构建的收益就被抵消了大半。真正干净的做法是把外层那个 SingleChildScrollView 去掉，让 _ProjectsSection 自己就是那个滚动容器；或者整页改成 CustomScrollView + SliverList.builder，让所有区块共用一个 sliver 滚动上下文。
最后这段是本次演练的价值所在。只答 ".builder 更省性能" 是 Pass；说清 shrinkWrap 的副作用并给出 Sliver 方案是 Credit 以上。

1 · 用户点了 New project，到项目出现在列表，完整发生了什么？
context.push('/projects/new') → go_router 匹配 GoRoute → ProjectFormScreen → 填表 → _save() 置 _submitted 并 _validate() → context.read<ProjectsProvider>().createProject() → dio POST（拦截器挂 token）→ ProjectCard.fromJson → _upsertMine 造新 List → notifyListeners() → 首页 context.watch 的 _HomeTab 重建 → 新项目出现。
2 · context.watch 和 context.read 分别什么时候用？用反了会怎样？
build() 里 watch（订阅，数据变了会重建），回调 / initState 里 read（只取一次）。build 里用 read → 数据变了 UI 不刷新；回调里用 watch → 在错误的生命周期建立订阅。
3 · notifyListeners() 之后发生了什么？
ChangeNotifier 遍历监听者列表逐个回调 → 由 context.watch 注册的 element 被标记 dirty → 下一帧 Flutter 重新调用它们的 build。不是立刻重建。
4 · 为什么 _loading = false 一定要放在 finally？
放 try 末尾的话，一旦抛异常就跳过，UI 永远卡在转圈。
5 · 为什么每次都造新 List 而不是 _mine.add(card)？
① getter 直接暴露列表，原地改能绕过 provider 且不触发通知 → 状态变了但 UI 不刷新，极难查；② 不可变快照更安全。
6 · whereType<Map<String,dynamic>>() 干什么？
过滤掉不是该类型的元素，同时把静态类型收窄。一条脏数据不会炸掉整个列表。
7 · .map(ProjectCard.fromJson) 为什么可以不写参数？
构造函数撕裂（tear-off）——把构造函数当作一个函数值传进去，等价于 .map((j) => ProjectCard.fromJson(j))。
8 · factory 构造函数和普通构造函数的区别？
factory 不强制返回新实例，可以做解析、返回缓存、返回子类实例。所以 fromJson 都是 factory。
9 · 为什么模型字段都写 as String? ?? ''？
防御式解析。后端并行开发，字段可能缺或类型不对；不兜底就会抛异常，一条坏数据白屏整个列表。
10 · 为什么用 DateTime.tryParse 不用 DateTime.parse？
parse 失败抛 FormatException，tryParse 返回 null。解析层的原则是永不抛异常。
11 · token 存在哪？每个请求怎么带上的？
shared_preferences 的 bp_access_token + 内存 _cachedToken；dio 的 InterceptorsWrapper.onRequest 统一挂 Authorization。
12 · 为什么 ApiClient 是单例？
私有构造 ._internal() + static final instance。全 App 共用一个 Dio → 连接池、拦截器、token 缓存都只有一份。
13 · handler.next(options) 不调会怎样？
请求卡在拦截器里永远发不出去。next 放行、reject 直接失败、resolve 返回假响应。
14 · 截图上传为什么要两个 Dio？
第二步是发给 S3 不是我们后端。预签名 URL 本身是凭证，多带我们的 Bearer 会和签名冲突被拒。_storageDio 没有拦截器。
15 · 为什么不让后端代传图片？
流量走两遍、后端要扛大文件并发。预签名让字节手机直达 S3，后端只处理两个轻 JSON，鉴权和元数据仍在后端手里。
16 · addPostFrameCallback 为什么必要？
直接在 initState 调会在 build 期间触发 notifyListeners → "setState called during build" 报错。推迟到本帧渲染完之后就安全了。
17 · initState 和 dispose 各在什么时候调？
State 创建后一次 / State 永久移除时一次。凡是 initState 里订阅或创建的，dispose 里必须释放，super.dispose() 放最后。
18 · 不 dispose TextEditingController 会怎样？
它是 ChangeNotifier，监听关系不断 → 内存泄漏；异步回调还可能对已销毁的 widget setState。
19 · IndexedStack 和条件渲染的区别？
IndexedStack 保留所有子节点的 State（换 tab 不丢滚动位置和表单内容），代价是全部都会被构建；条件渲染只建一个但会销毁另一个的 State。
20 · 宽屏窄屏是怎么切的？为什么用 LayoutBuilder 不用 MediaQuery？
LayoutBuilder 拿 constraints.maxWidth 和 kWideLayoutBreakpoint = 700 比。LayoutBuilder 量的是"我被分到多大"，MediaQuery 量的是整块屏幕——嵌在侧栏里的组件用 MediaQuery 会判断错。
21 · 断网了 Plaza 为什么还有内容？
每次成功请求把原始 JSON 存进 shared_preferences，失败时回落。只缓存无筛选的那份，否则会拿一份筛过的数据冒充全量。_feedFromCache 让 UI 打 OFFLINE 角标。
22 · Form 和 validator 你为什么没用？
见 §02 ⑤。要点：_submitted 实现"提交后才报错"、stage 徽章不是 FormField 管不到；并主动说 autovalidateMode.onUserInteraction 能达到同样效果、重构会换过去。
23 · ListView 和 ListView.builder 的区别？你为什么用了前者？
见 §02 ⑥ + §10 演练三。能当场改，并说清 shrinkWrap 的副作用。
24 · 条件导入是什么？为什么运行时 if (kIsWeb) 不行？
编译期分支。dart:io 在 Web 上不存在，直接 import 会编译失败——运行时判断救不了，那时代码已经编进包里了。
25 · abstract final class 是什么？
Dart 3 类修饰符：不可实例化 + 不可继承 = 纯静态常量容器。用类型系统守住"单一颜色来源"这个约定。
26 · 这个项目你写得最满意 / 最不满意的一段是什么？
最满意：connection_tuning_io.dart 的 idleTimeout（§02 ④）——它是真事故的复盘，能讲出完整故事。
最不满意：_HomeTab 那个 height * 0.5 的三层嵌套滚动（§11）——为了"各占半屏"用了魔法数，应该改成 CustomScrollView + Sliver。
这道题几乎一定会被问，两个答案都要准备好。
